# Technical Provably-Fair Assessment — winna.com VIP Slide

*Prepared by an independent provably-fair engineer.*

## Executive Summary

A VIP player at winna.com was offered a custom “slide”, who argued that he had results being manipulated to his disadvantage. After analysis of the situation, we have concluded that whilst we cannot prove manipulation, the custom slide product has been incorrectly advertised as provably fair.

## Provably Fair Background

Provably Fair Games come in two shapes: instant and scheduled. There are various implementations of these, but we will here discuss the way winna.com implements both.

In both cases there are two facets of the PF algorithm:

- Proving that the bet was not manipulated by repeating the result.
- Proving that the seeds and algorithm used are fair.

### Instant PF

In an instant game (such as mines, dice, limbo), the PF is constituted of 3 pieces: the server seed (whose hash is communicated with the player), a client seed (i.e. a key used by the player, and which the player can choose to change) and a monotonically incrementing (per bet) nonce.

A hash of the server seed + client seed + nonce is used to generate random numbers from it.

**How is the player protected?**

- The client seed can be controlled by the player. Player is allowed to rotate/change the client seed.
- The nonce generates a totally different result when incremented: Operators cannot predict easily a “good” server seed that will yield profit to them.

### Scheduled PF

The way winna.com implemented their scheduled PF in a manner like stake.com: A server seed is generated, from which 10 million other server seeds are generated. This is done by hashing the previous seed to generate the next seed. The last server seed is publicly shown. The operator then commits to a particular bitcoin to be mined, the block of which is used as the client seed.

The random numbers are generated by taking the hash of a server seed + client seed.

**How is the player protected?**

- The player can verify that a server seed can be recursively hashed until you arrive to the last publicized seed.
- The client seed choice is not in the control of the operator.
- Therefore, the operator cannot control what the next outcome will be.
Games like Slide and Crash are traditionally implemented in this way.

## Implementation of Provably Fair for Custom Slide

When the bets in question are verified against the winna.com’s provably fair validators, the outcomes match the input seed information. Repeatability of the outcomes IS NOT the issue here. The issue is the choice of seeds.

Initially we thought that the custom slide game was using a traditional scheduled PF algorithm. This is because the client seed used was the hash of a mined bitcoin (traditionally used for a scheduled PF). However, when we took the server seed used by the bets in question, there was no hash-link between the different server seeds.

After enquiring why the server seeds were not hash linking, we confirmed with winna.com that for the custom slide game, a “limbo-model” (i.e. instant PF) was used, but the nonce was always pegged to 0 and server seed always changing PER BET.

## Conclusion

The challenge here is that it is very unorthodox and prone to manipulation:

- A scheduled game using an instant provably fair algorithm.
- In addition, the client seed used was a mined bitcoin hash, with the player having no means of changing it.
- A server seed is always changing per bet for an instant bet. (Server seeds do change for scheduled games, but they hash-link to the last/publicized server seed)
- Server seeds do not hash-link with each other, or a final committed server seed.
- The nonce is pegged to 0.
Whilst we cannot directly prove fraudulent activity, the above is enough proof that the game was not provably fair, and one needs to trust the operator solely that no manipulation was done. The operator had in control all variables and could have fabricated the outcomes (known client seed that wasn’t modifiable, nonce at 0 and always changing server seed).
